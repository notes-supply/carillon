# T3 runtime

A Carillon runtime provider that executes turns on a [T3 Code](https://github.com/pingdotgg/t3code) server instead of Pi. It is a separate execution runtime behind the same runtime boundary core already speaks: `POST /v1/turns`, `GET /v1/turns/{id}/activity`, `GET /v1/environment`, `GET`/`PUT /v1/model`, `GET /v1/commands` and `/health`, authenticated with the installation credential and fail-closed before any T3 work. The boundary itself (HTTP adapter, failure display rules, tool descriptions, registry loading) comes from the shared [`@carillon/runtime`](../runtime/README.md) package; this package depends on no Pi or Discord code. The public entry point is [`src/index.ts`](src/index.ts); importing it opens no connection.

```ts
import { createT3Runtime } from "@carillon/runtime-t3";

const runtime = createT3Runtime({
  endpoint: { url: "http://127.0.0.1:3773", token },
  projectId: "…",
  selection: { instanceId: "claudeAgent", model: "claude-fable-5-1", options: [{ id: "effort", value: "high" }] }, // the agent default
  workspace: "/path/to/workspace",
});
const answer = await runtime.executeTurn({ correlation_id: "turn-1", interface_id: "discord", agent_id: "default", audience_id: "conversation-1", input: "Hello", resource_root: "…", attachment_root: "…" });
```

## Ownership

Carillon owns admission, turn identity and delivery. T3 owns execution, its transcript, jobs and provider policy. The runtime stores nothing: every T3 identifier it needs is derived from Carillon's own facts, encoded so that no fact can run into the next ([`contracts.ts`](src/contracts.ts)):

- one T3 thread per conversation (project, interface, agent, audience), opened by a `thread.create` command whose ID is derived from the thread's, so opening it again replays the command's receipt instead of creating another thread;
- one T3 message per Carillon turn, dispatched by a `message.dispatch` command derived from the turn's correlation ID. T3 keeps a receipt per command, so the same turn can never produce two runs. T3 commits a run with its accepted receipt in one transaction and keeps a rejected receipt only for a command that committed nothing, so a dispatch T3 answers with a failure is replayed once to read that receipt back: a rejected receipt means nothing of the turn is on T3, an accepted one means the run exists and is observed, and any other answer leaves the turn's work possibly running;
- the turn's run is the one whose `userMessageId` is the turn's message.

## How a turn runs

Turns of one conversation run one at a time, in order; turns of different conversations (different threads) run at once, so a registry entry may set `parallel_turns` for this runtime. `executeTurn` ([`runtime.ts`](src/runtime.ts)) refuses attached files (not supported yet), opens one WebSocket to T3 ([`t3.ts`](src/t3.ts)), ensures the thread and subscribes to it, asking for T3's bounded snapshot (recent messages and items; runs, requests, provider threads, sessions, child agents and context transfers whole) and a completion marker. If the thread has no run for this turn, the message is dispatched as the person wrote it (a command invocation verbatim, prose with a note naming earlier files this runtime cannot provide). It carries no model selection, so it runs with the thread's own. Work already running on the thread is never interrupted, whoever started it (an earlier turn's late wake, or the person in T3's own UI): the message is dispatched with `queue_after_active` and waits in T3's queue, and the turn reports the `queued` phase until its run starts. From then on the subscription drives a bounded fold of the thread's state ([`watch.ts`](src/watch.ts)) until the outcome is known. The fold keeps only the turn's own facts: its run and the runs T3 started after it, earlier runs still active, the tools running now and the last few finished, open requests, the turn's assistant messages (kept across a bounded snapshot that omits earlier ones, and replaced by ID when a snapshot lists them), the child agents and context transfers of its runs, the provider thread's roster and session. A snapshot lists runs whole, so one that omits a run the turn observed is refused as malformed rather than read as that run having stopped. History outside the turn is dropped as it arrives, and the turn's run is kept as its identity even if a later snapshot does not list it. T3 sends a run's provider thread record just before `run.created`, and its session record just before the thread record that names it when the turn starts, so the fold holds the few most recent provider records it cannot yet attribute and adopts them once the run or thread refers to them. A session record the fold has not seen is unknown, never detached: detachment is T3's own `provider-session.detached`, a thread that names no session, or a snapshot that omits the session a turn thread names.

**Completion** requires more than a settled session, and is decided from T3's state alone, never from a timer. The turn owns its run and the runs T3 starts after it only when they can be its own: this turn's wake can start only after its run completed with work still listed, so a later run first seen while the run is still active is another process's (such as an earlier turn's late wake) and stays foreign, neither awaited nor answered with; the next turn waits behind it if it is still active. After the run completed, a later run is the owed wake or resolves a resumed snapshot's ambiguity. A later run no fact of this turn accounts for, as in a fresh snapshot that shows a completed run and a completed follow-up with nothing seen in between, is a stray: the turn ends unresolved rather than answering with the acknowledgement alone or with text of unknown origin. T3 labels every wake alike (`createdBy: "agent"` on the same provider thread), so when a turn's stop was not confirmed the runtime remembers that thread as uncertain: later turns there still run and complete on their own run's text, but one that comes to depend on a follow-up ends unresolved with that explanation. The public contract offers no stop or delivery fence that would show the earlier process gone, so the fence is never lifted by inference; it lives in the runtime process and a restart forgets it. The last of those runs must be `completed`, no request of the turn may be open (whatever the run's status), and the provider thread must list no pending background work. A run that completed while its roster still listed work owes a follow-up: Claude delivers task notifications inside a running turn, so work that was still listed at completion is reported in a run of its own, and the turn waits for a later run however long it takes. T3 projects no "wake pending" fact; if T3 reports the provider session stopped, the owed report cannot come and the turn fails with that explanation; if the session was merely detached, T3 removes its record before the process closes and does not fence what it may still deliver, so the turn fails saying that T3 does not confirm whether the result will still arrive. The facts "work was listed for this turn's run" and "the run completed while work was listed" survive snapshots: a resumed subscription that only shows a completed run with an empty roster cannot tell whether the result reached the running turn or is still owed, so the turn fails closed as unresolved, after the same stop, rather than report the run's text as the answer. The turn's request items also survive snapshots, so a request T3 still lists pending keeps its ownership and wording even when the bounded history window omits its item. The answer is those runs' assistant messages in order; an empty answer fails the turn. A `failed` run is explained with T3's own failure text, which passes the shared runtime package's display boundary before it reaches a conversation. A failed or otherwise stopped run whose provider thread still lists background work is not quiet: before the turn ends and the next may start, that work is stopped through the same path a cancellation uses, and the explanation adds only what T3 confirmed about the stop. A pending request belongs to the turn only when one of the turn's own request items names it; a run that waits before that item has arrived is unknown, not blocked. A run someone else stopped, or one waiting for an approval or answer this runtime cannot give, is reported as an actionable failure: the question or request kind is named, the run is interrupted so the thread is usable again, and the explanation says only what T3 confirmed: that the run stopped, that it ended but the request is still open, or that T3 did not confirm the stop.

**Delegated work.** A run can delegate to T3's own child agents (`delegate_task`, in async or wait mode). T3 owns their execution and the delivery of their results: when a child finishes, T3 publishes its result, announces a continuation message on the parent run (`delegatedCompletion`) and then starts that continuation as a run of the thread, queued behind active work; a wait that times out does not cancel the child, it switches the task to the same continuation. The fold links a continuation to the turn only through those native records (the parent run's announced message, or the message's own `delegatedCompletion.parentRunId`), whenever it is seen, so a continuation is never mistaken for a late wake or a stray. The turn answers when its own runs (and any owed wake) are done; the parent's reply is delivered then, while its children work. When work it started still owes the conversation a report (a T3-owned child still working, a result T3 has yet to deliver, an announced continuation not run, or a continuation no turn answered with), the answer carries a follow-up cursor (`{ message, after }`): the message the turn began with and the last run it answered for. Core queues a follow-up turn of the same conversation with that cursor; that turn dispatches nothing, anchors on the same message, adopts only the continuations T3 started after `after`, waits while the work still owes a report, and delivers their text through ordinary delivery, carrying another cursor when the continuation delegated in turn. T3 keeps a child active while its own descendants work, so the parent thread's records reconcile nested work natively. A follow-up turn stops nothing and leaves the uncertainty fence alone: the continuations are T3's. When the delegated work ends without a report (cancelled and disposed), the follow-up turn says so. This runtime never reads results through the agent-facing `task_status`, which acknowledges them; it only reads the thread's own records.

**Reconnection.** A lost connection, or a lost answer to a command, never repeats work. Until the turn may have reached T3 (dispatched by this call, or read back from a run the thread already had for it), cancellation ends protocol discovery, the upgrade, the first-snapshot wait and reconnect delays. Thread-creation and interrupt RPCs already awaiting a receipt remain bounded by their timeout. Cancellation is rechecked immediately before dispatch, so a turn already cancelled at that boundary is not sent; once work may exist, recovery continues so it can be found and stopped. The next connection resumes the subscription after the last event sequence the fold saw, so T3 replays only what was missed (or sends a bounded snapshot when the gap is too old); a run that exists is adopted, and only a turn T3 has no run for is dispatched again, under the same command ID. Reconnections are bounded; when they run out, or when T3 can no longer be reached, refuses the credential or changes protocol after the turn's work may exist, the turn fails naming the native run that may still be running.

**Cancellation.** When core disconnects (the HTTP request closes) or the runtime closes, the runtime sends `run.interrupt` for the turn's own active (or queued) run, or for the thread's latest run when only background work remains (T3 settles a stopped thread's background work through its latest run), waits for T3 to report no active run, an empty roster and no report still owed by a live process, and logs how many tool calls had started. It never interrupts a run it did not start. When nothing runs but the process still owes a report (the roster cleared before its wake), T3 refuses the interrupt; the runtime then requests the public `provider-session.detach`, the only stop T3 offers for that state. T3 accepts the request, removes the session's record and closes the process afterwards, without confirming the closure or fencing a wake the process may still deliver, so the runtime reports that stop as unconfirmed and never as ended. Those are not undone. A cancellation that arrives while the dispatch is in flight waits for the dispatch's answer or the run's appearance before interrupting. If T3 does not confirm the stop in time, the runtime says so rather than claiming a stop, and the conversation's later turns wait behind whatever still runs.

**Activity.** `activity(correlation_id, interface_id)` answers only for the interface the turn serves. It is derived from T3's timeline items: running and recently finished `command_execution`, `file_change`, `file_search`, `web_search`, `dynamic_tool` and `subagent` items, pending background work, and the first line of the model's latest public message. The phase is `queued` while the turn's run waits in T3's queue and `waiting` while its run (or, for a follow-up turn, the delegated work) waits. Delegated and transferred work is the shared bounded `work` summary: each child agent of the turn's runs (T3-owned or provider-native) as a `delegation` with the state T3 last confirmed, its title and model, nested under another listed child when T3 says so; the report T3 still owes the conversation as a `task`; provider handoffs, forks and merges of the turn's runs (spawn and result transfers belong to their delegation and are not listed). A child shows once: not also as its `subagent` item or as its parent's background task. A child a resumed snapshot no longer lists is `unknown` and the summary partial, never finished. Prompts, progress text and results are never shown. Each answer is assembled from the bounded state the fold keeps, not from a scan of the thread. `tool_calls` counts the distinct tool items of the turn; their IDs (not bodies) are kept for the turn's lifetime, because item identity is the only deduplication the contract guarantees across updates, replay and snapshots. That set, like the turn's child agents, is proportional to the turn's own work, which is the accepted bound. Commands and file paths are described with the shared runtime package's deny-by-default descriptions and credential redaction; reasoning items and tool output are never shown.

## Protocol

The runtime speaks T3 orchestration protocol 2 only: `orchestration.dispatchCommand` with the V2 commands `thread.create` and `message.dispatch` (with `createdBy` and `creationSource`; there is no `createdAt` and no legacy `thread.turn.start`), `run.interrupt` and `provider-session.detach`, and `orchestration.subscribeThread` with `acceptBoundedSnapshot`, `requestCompletionMarker` and `afterSequence`. T3 windows a bounded snapshot's messages and timeline items (recent user turns, item and byte limits); runs, requests, provider threads and sessions arrive whole. `turnLimit` and `beforeCursor` belong to T3's paged HTTP thread reads (`threadSnapshotPagination`), not to the subscription. Before sending a credential it checks T3's discovery answer and refuses any other version. The upgrade uses `/ws?orchestrationProtocol=2` with a bearer token T3 issued (`t3 auth session issue`); the token is read from a file and never passed on the command line or logged. Every answer is validated against the subset of T3's contracts the runtime consumes ([`contracts.ts`](src/contracts.ts)): timeline kinds are discriminated, each with the fields the runtime reads required, so a known kind missing them fails the turn as "a form this runtime does not understand", never a guess; kinds the runtime does not read are ignored, not retained.

## Settings

The service reads the registry for its own entry and `providers/<id>.toml`, checked strictly:

```toml
url = "http://127.0.0.1:3773"           # T3's HTTP origin (https for a tailnet)
token_file = "credentials/t3.token"     # relative to the installation
project_id = "…"                        # the T3 project whose workspace is the agent's
title = "Carillon"                      # optional thread title prefix

[model]
instance_id = "claudeAgent"
model = "claude-fable-5-1"

[model.options]
effort = "high"                         # a select's choice ID, or true/false for a boolean
```

`[model]` is the agent default: the selection a conversation's thread is opened with, as T3 names it. Run it from the repository with:

```sh
bun packages/runtime-t3/src/cli.ts --config "$CARILLON_HOME/carillon.toml" --provider runtime-t3 --token-file "$CARILLON_HOME/credentials/runtime-t3.token"
```

The release ships the same program as the standalone executable `app/bin/carillon-runtime-t3` and registers the optional user unit `carillon-runtime-t3.service`, which runs that command with the installation's registry and `credentials/runtime-t3.token`. The default target does not want the unit: add the `runtime-t3` provider to `carillon.toml`, write `providers/runtime-t3.toml` and the two credentials (the installation token and the T3 token file), then enable the unit without starting it on its own (`systemctl --user enable carillon-runtime-t3.service`) and start or restart Carillon through its target (`carillon restart`, or `carillon start` when it is stopped), so the service runs under `carillon.target` like the others and Carillon's update and stop know it is running. Uninstall removes the unit with the others.

Startup fails closed: the registry entry must exist and be enabled, the installation credential must match, the settings file must be valid, and T3 must answer discovery with protocol 2 and accept the token.

## Models

The conversation's model is its thread's own selection, as T3 holds it: every message runs with it, and it changes when the person changes it here or in T3's own UI, the last change winning. Nothing is stored on the Carillon side ([`models.ts`](src/models.ts)). `GET /v1/model` reads T3's catalogue from `server.getConfig` (the models of provider instances T3 reports enabled, installed and usable, with their select and boolean settings; a boolean is offered as `on`/`off`) and, in a conversation, the thread's selection from its snapshot. A conversation whose thread does not exist yet shows the agent default, which it will start with; reading creates nothing. The agent default is `[model]` above and is marked read-only, so `/model` shows it without controls; changing it means editing this file and restarting.

`PUT /v1/model` for a conversation sets the thread's selection with `thread.model-selection.set` (opening the thread first if needed), then reads it back. T3 accepts any model name and setting value, so the change is checked against the catalogue first. It waits in the conversation's queue, so a turn that arrives meanwhile runs with it, and it is refused while a turn of the conversation is queued or running or while T3 still works or owes results on the thread: T3 may restart or replace the provider session to apply a change, which would end that work. `expected` is compared with the thread's selection just before the change; T3 has no compare-and-set, so a change made in T3's own UI in between is overwritten. T3 decides whether a change it accepts needs a new session or a handoff to another provider, and its refusal is reported as given. Returning the conversation to the agent default sets `[model]` on the thread.

## Commands

`GET /v1/commands` lists what T3's own composer offers in the conversation ([`commands.ts`](src/commands.ts)): the slash commands, then the enabled skills a person may invoke (`userInvocable` not false), of the conversation thread's provider instance (or the agent default's, before the thread exists), for the agent's workspace. It asks `server.refreshProviders` with that instance and workspace, which scans the workspace once if T3 has not; later scans follow T3's own schedule. A name listed twice is offered once, and a name over 100 characters is left out. A turn with `native.intent: "command"` is dispatched verbatim, and T3 runs it as it runs the same text typed in its own UI. When such a run completes without an assistant message (a compaction, for instance), the turn answers with a short note naming the command instead of failing as an empty answer; a prose turn without an answer still fails, and a failed command keeps T3's explanation.

## Resource snapshot

T3 has no system-prompt facility for a thread, and Carillon writes nothing into the T3 project. The agent's instructions and skills for T3 are the project's own native configuration: its workspace's `CLAUDE.md` and `.claude/skills/<name>/SKILL.md`, which the native provider loads for every session in that workspace (not per thread; `CLAUDE.md` is read when a session starts). The resource snapshot's `SYSTEM.md`, `AGENTS.md`, Pi extensions and skills are Pi's and are not sent: per-turn snapshot semantics remain Pi's. Files attached to a turn are refused with an explanation; files of earlier turns that core offers again are named in the message as unavailable, so the model and the person know.

## Tests

[`fake.ts`](src/fake.ts) is a test fixture: a double of the parts of T3 this runtime uses, with sequence-based replay, completion markers, provider sessions, T3's settlement of background work through the latest run, delegated child agents with their continuations in the serving build's event order, context transfers, and injectable faults (dropped answers, dropped requests, delayed answers, rejections, malformed frames, ignored interrupts, snapshot-only resumes, contradictory open requests, stalled discovery and upgrades, and disconnections). [`runtime.test.ts`](src/runtime.test.ts) proves continuity, lost-receipt recovery without a second run, reconnection by replay and by snapshot, cancellation including the in-flight dispatch race, background work left by a completed run, waiting behind runs this runtime did not start (an earlier turn's late wake, the person's own run in T3) without interrupting them, the parent reply and its follow-up report of delegated work, blocked runs with truthful stop reports, requests still open after a terminal run, late wakes and a session that ends before its wake, failed runs, activity, malformed known timeline kinds, fail-closed transport failures and attachment refusal. [`watch.test.ts`](src/watch.test.ts) covers the bounded fold and [`t3.test.ts`](src/t3.test.ts) the client.
